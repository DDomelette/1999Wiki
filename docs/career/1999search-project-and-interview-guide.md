## 二、90 秒项目介绍

我独立主导开发了 1999Search，它是一个面向《重返未来：1999》知识场景的 RAG 问答和富媒体 Wiki 项目。从规划到完整落地用了一个月。

这个项目不只是把向量数据库接到大模型上。我先建设了灰机 Wiki 的数据采集和加工链路，把 7,456 个实体页面处理成 8,246 个父块、16,010 个子块和 15,758 条媒体绑定，然后分别写入 MySQL、Milvus 和 MinIO，为 Wiki 展示与 RAG 问答提供统一数据源。

检索侧采用结构化取数、BM25 和 BGE-M3 稠密向量的混合方案，并增加实体消歧、多意图规划、Owner 约束、父子块扩展和上下文预算。回答侧实现了来源编号、引用校验、修复与安全回退，使同步请求和 SSE 最终消费同一份冻结结果。

产品侧使用 FastAPI 和 React 完成聊天、会话记忆、分类浏览、人物详情以及图片、语音、视频展示。工程侧建立了 Provenance 校验、Fail-closed 启动、Shadow Collection、自动化测试和全链路评测。

我采用人工主导的 AI 原生研发方式，通过 Codex、Trae Solo、Kimi CLI、MCP 和 ACP 编排 AI 与多 Agent，但需求、架构、任务拆分、代码审查、风险处理和最终验收都由我负责。这也是项目能够在一个月内完成复杂全栈闭环的主要原因。

## 四、你具体完成的工作

### 1. 产品与需求规划

- 将最初的知识问答想法拆解为数据采集、语料构建、RAG、媒体、Wiki、API、前端、基础设施和评测模块。
- 明确 Wiki 与 RAG 的边界：共享数据来源和媒体对象，但 Wiki 使用 MySQL，RAG 使用 BM25/Milvus，避免展示层与检索层互相污染。
- 为自由补充、引用、会话记忆、媒体展示和索引切换定义授权与失败边界。
- 将复杂需求沉淀为设计、实施计划、运行手册和验收门禁，减少 AI 协作中的上下文漂移。

### 2. 数据采集与知识工程

- 实现灰机 Wiki API、浏览器与 CDP 相关的数据采集能力，包括凭据管理、账号校验、断点状态和完整性检查。
- 处理 data pages、普通页面、Wikitext 与资源清单，构建统一的 crawler snapshot。
- 将原始数据规范化为实体、父块、子块和媒体绑定，并为异常数据生成显式排除证据。
- 建设 MySQL Wiki 投影、BM25 索引、Milvus 向量集合和 MinIO 资源链路。
- 完成 7,456 个实体页面、8,246 个父块、16,010 个子块、15,758 条媒体绑定的当前有效数据闭环。

### 3. RAG 与检索算法

- 设计规则与 LLM 结合的 Query Planner，识别实体、别名、类别、主要意图和次要意图。
- 对同名或归属不明实体保持未解析状态，避免模型凭空猜测。
- 融合结构化精确取数、BM25 稀疏检索和 BGE-M3/Milvus 稠密检索。
- 使用加权 RRF 合并候选，并加入实体匹配、意图匹配、质量惩罚和 Owner Gate。
- 根据多意图需求进行父子块扩展、兄弟窗口补全和确定性上下文预算分配。
- 设计可选 Reranker、候选过采样和检索失败分类。

### 4. 可信回答与评测

- 将最终检索结果映射为请求级 S01、S02 等来源编号。
- 设计引用格式检查、引用有效性验证、一次自动修复和安全回退。
- 冻结检索包与响应包，使同步接口和 SSE 不会在传输阶段重新检索或篡改答案。
- 区分 Grounded、Ungrounded 和无回答等状态，防止自由回答冒充知识库事实。
- 建设 RAG 全链路评测、模块评分、回归快照、隔离探针和可观测性记录。
- 能够诚实识别当前真实评测中的无依据陈述、意图丢失、媒体类型和 Span 完整性问题，并继续收口，而不是只展示成功案例。

### 5. 后端与会话系统

- 使用 FastAPI 实现健康检查、同步问答、SSE 问答、会话删除、媒体分页、分类和 Wiki API。
- 设计同步与 SSE 共用的单次执行服务，避免两条链路产生不一致结果。
- 实现带租约、TTL、LRU、并发隔离和完成后提交的进程内短期会话存储。
- 确保客户端在 SSE 完成前断开时不提交不完整会话。
- 使用 Pydantic 契约限制对外字段，避免本地路径、内部状态或未批准信息泄露。

### 6. React 全栈交互

- 使用 React、TypeScript、Vite 和 Zustand 实现聊天状态、会话 ID、SSE 消费和中断控制。
- 构建 Wiki 分类、页面列表、搜索、人物选择、详情阅读和结构化内容渲染。
- 建设图片、立绘、技能图、语音、视频和 Live2D 等富媒体展示及降级逻辑。
- 实现响应式布局、主题切换、滚动导航、动效策略和 Reduced Motion 兼容。
- 使用 Vitest、Testing Library 与 Playwright 覆盖组件、状态、API 和 E2E 行为。

### 7. 基础设施与数据安全

- 编排 Milvus、MinIO、MySQL 和本地前后端服务。
- 设计 Hash-pinned Provenance Baseline，验证原始快照、加工产物、BM25 和活动 Milvus 集合身份。
- 采用 Fail-closed 策略：数据不一致时只开放健康诊断，RAG 接口返回 503。
- 禁止运行时自动重建或覆盖活动集合，只允许创建显式命名的新 Shadow Collection。
- 为 MinIO 迁移、对象一致性、资源绑定和回滚前检查保留审计证据。

### 8. 测试、文档与工程治理

## 九、五模块评测体系怎么讲

### 1. 为什么要拆成五个模块

可以这样回答：

> RAG 的最终回答不准确，根因可能在服务没准备好、实体或意图识别错误、证据没召回、模型无依据生成、媒体绑定错误，或者链路本身不稳定。如果只看一个总分，很容易用下游 Prompt 调整掩盖上游问题。因此我把评测拆成 M1 到 M5，并强制按上游到下游定位和复测。

五个模块分别是：

- **M1 就绪与数据一致性：** 验证后端、Milvus、MinIO、回答模型和 Artifacts 能真实访问，活动 collection 与配置一致，评测前后受保护数据快照完全相等。
- **M2 查询理解与检索：** 同时检查实体、实体类型、主意图、次意图、媒体意图、Recall@K、MRR、nDCG、意图覆盖、预算 Shortfall 和跨实体泄漏。
- **M3 回答与证据一致性：** 使用独立 LLM Judge 评估 Groundedness、Relevance、Completeness 和 Refusal Correctness，再用确定性规则检查引用是否存在、是否真正支持对应声明。
- **M4 媒体与响应契约：** 检查媒体类型是否符合意图，Owner/Parent/Child/Event 绑定是否准确，语音分页集合是否完整，URL 是否可播放，以及同步与 SSE 是否返回同一语义结果。
- **M5 可靠性与性能：** 检查请求成功率、重复请求的一致性、结构化异常，以及 Planning、Retrieval、首 Token 和完整回答的 P95。

### 2. 分级制度

系统使用“数字越小越严重”的等级：

| 等级 | 含义 | 结论 |
|---|---|---|
| PASS | 所有门禁和目标满足 | 通过 |
| SEV-4 | 不影响验收的优化提醒 | 通过 |
| SEV-3 | 低于质量目标但仍高于最低线 | 有条件通过 |
| SEV-2 | 某个关键模块的 P0 门禁失败 | 不通过 |
| SEV-1 | 链路能运行但结果不可信 | 不通过，禁止发布 |
| SEV-0 | 链路无法执行或无法产生证据 | 不通过，先恢复系统 |

每个模块独立产生等级，全局结果取最严重模块。即使平均分很高，只要出现跨实体来源、虚构引用、无依据事实或敏感路径泄漏，也不能被其他高分抵消。

### 3. 分难度、分意图和分宽容度

| 难度 | 场景 | 目标分 | 最低分 | 最低分通过比例 |
|---|---|---:|---:|---:|
| D1 | 实体和意图明确的标准问题 | 90 | 85 | 95% |
| D2 | 多意图、比较和跨段落整合 | 85 | 78 | 90% |
| D3 | 别名、口语、省略和错别字噪声 | 80 | 70 | 85% |
| D4 | 无资料、越界、诱导编造和应拒答问题 | 90 | 85 | 100% |

这里的“宽容度”不是对所有错误一视同仁地降低标准：

- D3 可以降低相关性和完整性最低线，因为输入本身有噪声。
- D3 不能放宽跨实体、错误引用、无依据断言、路径泄漏、服务错误和数据写入等硬门禁。
- D4 不降低拒答正确性；资料不足时诚实拒答、澄清或提供 Failure Action 本身就是正确完成任务。
- 每个支持的 P0 Intent 至少进入一个 D1 标准样本和一个 D2/D3 样本，多意图问题同时检查 Planner、候选和最终上下文是否真的消费了全部意图。

### 4. 分场景权重

- 文本问答：M2 40% + M3 50% + M5 10%。
- 纯媒体请求：M2 30% + M4 60% + M5 10%。
- 文本与媒体复合请求：M2/M3/M4 各 30% + M5 10%。
- 边界与拒答请求：M2 30% + M3 60% + M5 10%。

未适用模块不会按零分处理。例如纯媒体请求主要考察是否找对实体、媒体绑定是否准确和接口是否稳定，不会为了凑总分强行评价长文本答案。

### 5. 动态样本与复现

- 从当前 Parent、Child、Media Artifacts 和活动 Milvus collection 动态生成期望，而不是写死角色和数量。
- 唯一问题不少于 48 个：D1 至少 16、D2 至少 12、D3 至少 12、D4 至少 8。
- 至少覆盖 8 个不同体量的实体，以及所有当前支持的 P0 Intent。
- 至少 10% 的问题使用同配置重复请求，检查实体、意图、关键来源和媒体集合是否稳定。
- 使用固定 Seed、Pairwise Coverage、Run Manifest、Sample Manifest、Case Results、Module Summary 与评测前后快照保证结果可追踪。

### 6. 当前结果怎样诚实表达

当前保存的项目理解记录为：M1 PASS，M2=97.75、M3=96.74、M4=96.85、M5=97.55，但由于 M3 出现无依据声明等严重事件，全局仍是 SEV-1、`accepted=false`。

推荐回答：

> 这些分数说明主体能力和大多数样本已经稳定，但我的门禁规则不允许平均分掩盖严重错误。全局失败恰恰证明评测器能抓到高平均分下面的无依据生成、意图丢失和契约问题。我会先按 M1 到 M5 的依赖关系定位根因，再进行定向复测和全量回归，而不是直接把阈值调低。

## 十、备份与灾备怎么讲

### 1. 整体链路

```text
1999Search 源码与运行数据
  ├─ Backrest 统一管理
  ├─ Restic 代码仓库 / 数据仓库分离
  ├─ D:\1999Wiki_Backup 本地快照与恢复区
  ├─ Quarantine + Staging + RestoreTests
  └─ Tencent COS S3 兼容远端目标 / Rclone 指定桶接入
```

这套体系的重点不是“把目录复制一份”，而是：备份前固定候选对象和哈希，生成不可变快照，在隔离目录执行恢复，再逐文件对账，只有恢复证据通过后才允许执行删除、迁移或切换。

### 2. 本地仓库设计

- `1999wiki-code-local` 保存项目代码，仓库约 0.34 GiB。
- `1999wiki-data-local` 保存语料、图片/视频、Milvus、etcd、MinIO、MySQL Volume、Vectorstore 和项目素材，仓库约 24.19 GiB。
- 两个仓库合计约 24.5 GiB，物理位置为 `D:\1999Wiki_Backup\Repositories`。
- 代码与数据分仓可以使用不同保留与校验成本：代码保留最近 10 份，数据保留最近 3 份；同时保留小时 24、每日 30、每月 12 的时间桶策略配置。
- Backrest 统一管理 Auto Unlock、Forget、Prune 和 Check；代码仓库可执行全量读取校验，大体量数据仓库可使用比例抽样降低日常校验成本。

### 3. 恢复演练与删除保护

- 将远端 MinIO 清理候选下载至外部 Quarantine，保留 Bucket/Object Key 结构。
- 对每个对象记录 SHA-1、SHA-256 与 Size，避免只按文件名判断一致性。
- 将 Quarantine 写入 Restic Snapshot，再恢复到第二个隔离目录。
- 对 1,291 个对象、765,296,657 字节完成全量指纹比对。
- 任意对象缺失、Hash 不同、Restic Check 失败或 Restore 失败都会阻断 Operation Plan 和后续删除。

面试时可以强调：

> 我把“已经备份”定义为可验证的恢复能力，而不是命令返回成功。只有隔离恢复后的对象集合、路径、大小和哈希与原候选完全一致，备份才算通过。

### 4. 腾讯云 COS 与 Rclone

- Backrest 中配置了腾讯云 COS 的 S3 兼容 Restic Repository，使用广州区域 Endpoint。
- Rclone 使用 S3 Backend 与 TencentCOS Provider 接入指定备份桶。
- 当前权限可以访问指定 Bucket，但不允许账号级 ListBuckets，符合 Bucket 级最小权限思路。
- 密钥只保存在本地受控配置中，不进入 Git、简历、日志、评测证据和示例配置。
- Backrest/Restic 可直接使用 S3 Endpoint；Rclone 负责对象存储的独立接入、检查与运维能力。不要把它们错误描述成同一条命令链。

### 5. 当前边界

Backrest 的备份 Plan 当前配置为手动触发，自动 Schedule 处于 Disabled；因此面试时应说“已经设计并部署备份、保留、校验和恢复体系”，不要说“每天自动备份持续运行”。远端 COS 目标已经接入并存在 Restic 仓库结构，但不应虚构远端完整数据量、RPO、RTO 或跨区域容灾等级。
