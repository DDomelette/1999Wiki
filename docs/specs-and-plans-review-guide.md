# Specs 与 Plan 编写审查规范

日期：2026-07-07  
适用范围：`docs/superpowers/specs/**` 与 `docs/superpowers/plans/**`

## 目的

本文档用于审查项目中的 specs 和 plan 是否符合当前协作要求。

核心原则：

```text
Specs 负责整体架构设计和模块契约。
Plan 负责本轮执行步骤和强制验收门槛。
```

Specs 只能降低理解偏差，不能自动保证落地完整。真正保证落地的是 plan 中的逐项执行、测试和验收闭环。

## 职责边界

### Specs 应该负责什么

Specs 是面向项目长期演进的设计文档，应回答：

- 系统整体应该如何组织。
- 模块边界是什么。
- 数据流、接口契约、存储策略和关键技术栈是什么。
- 哪些规则不能违反，例如 RAG 与 Wiki 解耦、MinIO 资源不能重复存储、浏览器不能接收本地路径。
- 每个模块当前必须具备什么能力，哪些只是可部分支持，哪些属于未来演进。

Specs 不应写成逐文件施工单，也不应把每一步实现细节都展开到代码层。

### Plan 应该负责什么

Plan 是面向一次具体开发任务的执行清单，应回答：

- 本轮要完成 specs 中哪些 P0 条目。
- 每一步要改哪些文件或模块。
- 每一步完成后用什么命令、测试或真实数据验收。
- 哪些 P1 项作为可选任务，只有 P0 完成后才执行。
- 哪些 P2 项明确不进入本轮。

Plan 必须作为强制验收门槛。执行完成后，应按 plan 逐项自检，而不是只用“测试通过”替代需求验收。

## Specs 推荐结构

Specs 应按模块组织，并在每个模块内部划分优先级。不要先全局列 P0/P1/P2，再让审查者跨章节寻找上下文。

推荐结构：

```text
# <模块或系统>设计

## 1. 背景与目标
## 2. 总体架构
## 3. 模块 A
### 3.1 模块职责
### 3.2 P0 当前必须满足
### 3.3 P1 可部分支持
### 3.4 P2 未来演进
### 3.5 关键契约与限制

## 4. 模块 B
### 4.1 模块职责
### 4.2 P0 当前必须满足
### 4.3 P1 可部分支持
### 4.4 P2 未来演进
### 4.5 关键契约与限制

## 5. 跨模块数据流
## 6. 错误处理原则
## 7. 测试与验收方向
## 8. 与旧方案的关系
```

每个模块内的 P 级定义：

- `P0`：本轮落地或该模块可用所必须具备的能力。缺失即不能宣称该模块完成。
- `P1`：可以部分落地或只保留接口、占位、fallback 的能力。是否执行由 plan 决定。
- `P2`：未来迭代方向。本轮 plan 不应包含 P2 实现任务，只能在 Deferred/Out of Scope 中说明。

## Specs 条目编号

Specs 中的重要条目应使用稳定编号，便于 plan 引用和审查。

格式建议：

```text
<MODULE>-<PRIORITY>-<NUMBER>
```

示例：

```text
MEDIA-P0-01: Wiki 与 RAG 共用同一 MinIO bucket。
MEDIA-P0-02: 浏览器只能接收 HTTP URL，不能接收 D:\ 本地路径。
API-P0-01: /api/wiki/pages/{page_id} 必须返回页面可渲染所需字段。
FRONTEND-P0-03: PageIndex 必须显示标题、类型、摘要和缩略图。
RAG-P1-01: RAG 后续可通过 source_id/entity_id/title 解析 Wiki 路由。
ANIMATION-P2-01: 后续按 ReactBits 组件为各区域接入动效。
```

编号不需要覆盖每句话，只覆盖会进入实现、约束或验收的关键要求。

## Plan 推荐结构

Plan 应从 specs 的 P0 条目生成。主线只包含 P0；P1 可以作为可选任务；P2 不进入执行任务。

推荐结构：

```text
# <任务名>执行计划

## 1. 目标范围
- 本轮必须完成的 specs 编号。
- 本轮不做的内容。

## 2. 强制验收门槛
- 每个 P0 条目对应的验收方式。

## 3. 执行步骤
### Step 1: <任务>
- 对应 specs: MEDIA-P0-01, MEDIA-P0-02
- 修改位置:
- 实现要点:
- 测试:
- 验收:

### Step 2: <任务>

## 4. 可选任务
- 只放 P1。
- 必须标明执行条件。

## 5. Deferred / Out of Scope
- 只记录 P2 或本轮明确不做的内容。

## 6. 完成后自检表
- 按 specs 编号逐项打勾。
```

## Plan 验收要求

每个进入 plan 的 P0 条目都必须具备以下信息：

```text
specs 编号
实现位置
测试位置或测试命令
真实数据验收方式
失败时表现
```

示例：

```text
MEDIA-P0-02
要求：浏览器不能接收本地 D:\ 路径，只能接收 MinIO HTTP URL。
实现位置：src/huiji_wiki/builder.py, src/huiji_wiki/repository.py, backend/wiki.py
测试：tests/test_huiji_wiki_api.py
真实验收：打开一个真实角色页，检查 Network/API 响应中的 media url。
失败表现：前端图片区域显示占位，或响应中出现本地文件路径。
```

## 审查清单

### Specs 审查

审查 specs 时逐项确认：

- 是否按模块组织，而不是把所有 P0/P1/P2 分散到全局列表。
- 每个模块是否说明职责、依赖、输出和边界。
- 每个模块是否有 P0/P1/P2。
- P0 是否是真正的当前必需能力。
- P1 是否明确最低实现边界，例如“保留入口和 fallback”。
- P2 是否明确为未来演进，避免被误认为本轮任务。
- 是否存在互相矛盾的内容。
- 是否存在 `TBD`、`TODO`、含糊词或无法验收的描述。
- 是否明确关键技术栈和关键算法，例如 MySQL、MinIO object key、路由解析顺序。
- 是否明确旧方案中哪些保留、哪些废弃。

### Plan 审查

审查 plan 时逐项确认：

- 是否只把 specs 的 P0 作为主线任务。
- 是否为每个 P0 条目建立了执行步骤。
- 是否每个步骤都有测试或验收方式。
- 是否包含真实数据或集成验收，而不是只依赖 mock 单测。
- 是否把 P1 放入可选任务，并注明执行条件。
- 是否把 P2 放入 Deferred/Out of Scope，而不是进入执行步骤。
- 是否能在完成后按 plan 逐项自检。
- 是否存在“写了接口但未贯通数据”的风险。
- 是否存在“组件能渲染但真实数据不可用”的风险。

## Wiki 模块示例分层

以下是 Wiki 模块当前可参考的分层方式。

### 数据构建模块

P0：

- 从灰机爬虫数据生成 Wiki 可展示页面。
- 只读源数据，不破坏 RAG artifacts、Milvus 或已有原始资源。
- 重复执行时只覆盖 Wiki 自己的 MySQL 表。

P1：

- 为 RAG 后续跳转生成共享实体 ID、source_id 和 route 映射。

P2：

- 增量构建、管理后台、构建任务 UI。

### MinIO 媒体模块

P0：

- Wiki 与 RAG 共用同一 MinIO 实例、bucket 和对象命名规则。
- 前端只能接收 HTTP URL，不接收本地路径。
- Wiki 页面可显示真实 MinIO 图片。
- 上传幂等，冲突中断，不清空 bucket 或 prefix。

P1：

- 输出上传、跳过、冲突、缺失、本地不可用资源报告。
- 支持缩略图或衍生图字段，但不替代原始媒体。

P2：

- CDN、私有 bucket、权限策略、媒体中心。

### MySQL 与 API 模块

P0：

- 提供 categories、pages、page detail、search、routes/resolve API。
- page detail 返回前端渲染所需正文、媒体、关系、来源和 link spans。
- API 失败不影响主站其他页面。

P1：

- 更精细的搜索排序、alias fallback、分页游标。

P2：

- 专用搜索索引、后台编辑、版本管理。

### 前端 Wiki 页面模块

P0：

- `/wiki` 独立于三屏滚轮结构。
- TopNav、Sidebar、日历入口都能进入 `/wiki`。
- 页面结构满足 `右信息栏 < 左分类唤出时 = 条目列表 < 主阅读区`。
- 分类、搜索、条目列表、阅读区和右信息栏可用。
- 真实图片能显示，缺失时有固定尺寸占位。

P1：

- 不同 page type 使用不同基础模板。
- 关键词链接可点击跳转。
- Live2D 保留入口和 fallback。

P2：

- ReactBits 动效、复杂模板、关系图谱、Live2D 播放器。

### RAG 跳转边界模块

P0：

- Wiki 不等待 RAG 入库，也不修改 RAG 检索链路。
- 保留稳定 route 和 resolve API。

P1：

- RAG 输出来源后，可通过 source_id/entity_id/title 跳转 Wiki。

P2：

- RAG 答案内嵌媒体、跳转到指定段落、来源卡片增强。

## 完成判定

一次开发任务不能只因为单测通过就判定完成。完成判定应同时满足：

- plan 中所有 P0 项均完成。
- 每个 P0 项有测试或明确的手动验收结果。
- 跨层链路至少有一条真实数据验收，例如真实 MySQL + MinIO + API + React 页面。
- P1 未完成项已明确标记为未执行或延期。
- P2 未进入执行范围。

如果某个 P0 项只做了占位，应判定为未完成，而不是“部分完成”。
