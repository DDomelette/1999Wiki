## 1. Decision Summary

The old Story `profile` representation and the new source-backed Story
representation are not a uniform one-to-one rekey.

- A legacy Story Parent can be matched to one current Story Parent when the
  exact source title and source SHA-256 identify one candidate.
- A legacy Story Child usually expands into many stable Story step children
  from the same exact source.
- Selecting the first step, using array position, matching by title
  similarity, or declaring all new children independent new records would
  misrepresent the migration.

C8b will therefore support a narrowly gated one-to-many
`corrected_semantics` migration in the fidelity ledger. It will not restore
the old generic Story child, create a synthetic huge aggregate child, or
choose an arbitrary step as its successor.

Any record without sufficient exact source or revision evidence remains a
blocker.

The 2,152 ambiguous Child rows are not accidental collisions. Each legacy

children. Parent and Child mappings therefore do not agree under a
one-to-one contract.

The current snapshot also contains Story records whose stable IDs already
exist in the active corpus. Those records are handled by the exact-ID rule in
section 5; they are not automatically treated as new records.

## 3. Canonical Source Identity

For this decision, a cross-generation Story source identity is:

```text
exact normalized Data:Story/<story-id>.json title
+ exact source content SHA-256
```

The source-ref `kind` label is not part of the cross-generation identity
because the old and new projectors use different labels for the same source.
It remains recorded as evidence.

The following are never migration keys:

- display name or alias;
- fuzzy title similarity;
- list position or scan order;
- legacy or candidate record counts;
- chunk index;
- an ordinal generated by the projector;
- content similarity without exact source evidence.

For a current Story candidate, `<story-id>` parsed from the exact source title
must agree with its canonical `entity_id`, Parent ID, owner IDs, and Story
route/category fields. A disagreement blocks the entire source group.

## 4. Parent Migration Rule

### 4.1 Exact source identity, one legacy Parent, one candidate Parent

Outcome:

```text
corrected_semantics
```

Required evidence:

- one legacy Parent and one candidate Parent share the canonical source
  identity;
- the candidate uses `entity_type=story`, `category=story`, and
  `section_kind=story`;
- the candidate entity and owner IDs derive from the exact
  `Data:Story/<story-id>.json` title;
- both rows have complete source refs;
- the migration records `legacy_section=profile` and
  `candidate_section=story`.

This is not `preserved_rekeyed`: the section meaning, child set, summary, and
owner identity change.

### 4.2 Exact source identity is absent, conflicting, or non-unique

Outcome:

```text
blocked_ambiguous
```

The 26 currently unmatched Parents remain blocked unless a later read-only
diagnostic proves same-page revision lineage as specified in section 7.

## 5. Child Migration Rule

### 5.1 One legacy Child expands to one or more stable step children

Outcome:

```text
corrected_semantics
```

The fidelity contract may contain multiple `SemanticRecordLink` rows with
the same legacy Child ID only when every row belongs to one validated Story
expansion group.

An expansion group must satisfy all of the following:

- exactly one legacy Child;
- one or more candidate Story children;
- every row shares the canonical source identity;
- every candidate belongs to the canonical Story Parent derived from the
  source title;
- every candidate has a unique stable source token and a source ref precise
  to its JSON path;
- candidate IDs are unique and sorted deterministically for ledger output;
- every link uses `legacy_section=profile`,
  `candidate_section=story`, and `change_kind=corrected_semantics`;
- the group consumes all and only the candidate Story children belonging to
  that exact source identity.

The fidelity ledger emits one legacy record entry whose
`candidate_identities` contains the complete deterministic candidate set.
Every candidate in the set is marked consumed, so it is not also classified
as `new_source_record`.

The same group rule applies to the 44 sources that currently have one
candidate Child. This keeps one semantic rule for both one-child and
many-child Story expansion.

### 5.2 Candidate Child lacks stable source evidence

Outcome:

```text
blocked_ambiguous
```

No positional or counter-based fallback may close the migration.

### 5.3 Legacy Child has no proven source successor

Outcome:

```text
blocked_ambiguous
```

The 26 currently unmatched Children remain explicit blockers until section 7
is satisfied. They are not labeled source-removed because the accepted
taxonomy found no explicit source-removal evidence.

## 6. Existing Stable IDs and New Source Records

For a candidate Story record whose ID already exists in the active corpus:

- identical canonical row hash and identical owner/section semantics:
  `preserved_exact`;
- changed payload with an approved, exact source-backed semantic transition:
  `corrected_semantics`;
- changed payload without that evidence: `blocked_ambiguous`.

A Story record may be labeled `new_source_record` only when:

- it has complete exact source evidence;
- no active predecessor exists by stable ID, canonical source identity, or an
  approved revision-lineage mapping;
- it is not a member of a Parent or Child expansion group;
- the candidate identity is stable and unique.

New and old rows may coexist only when they represent distinct source facts
with independent stable identities. Coexistence is not a way to bypass a
missing migration link.

## 7. The 26 Unmatched Source Groups

Exact title with a different source hash is not sufficient by itself.

These records may move from `blocked_ambiguous` to
`corrected_semantics` only if a create-new, read-only diagnostic proves:

- the active and current records refer to the same stable Wiki page identity;
- revision IDs and source hashes establish a traceable old-to-new revision
  chain;
- the current source title resolves uniquely;
- no competing candidate source exists;
- the expected Story ID and owner closure are valid;
- Parent and Child evidence refer to the same revision transition.

If any condition is missing, the blocker remains. `source_removed` is allowed
only when the source inventory explicitly proves removal; it cannot be
inferred from a hash mismatch.

## 8. Fidelity Contract Changes

C8b may change only the minimum contract needed to represent an approved
Story expansion:

1. Group `SemanticRecordLink` rows by `(record_kind, legacy_id)`.
2. Continue rejecting duplicate `(record_kind, legacy_id, candidate_id)`
   triples.
3. Permit more than one candidate only for a validated Child
   `profile -> story` `corrected_semantics` group.
4. Reject mixed source identities, mixed change kinds, duplicate candidates,
   incomplete source evidence, wrong owners, and partial source groups.
5. Add `("profile", "story")` to the section-correction allowlist only under
   the Story-specific source and owner gates.
6. Emit all candidate IDs in one deterministic fidelity-ledger row and mark
   every target consumed.
7. Preserve the existing one-to-one behavior for every non-Story record.

No general-purpose one-to-many reconciliation API is authorized.
